# IFC workflow (0.8.12)

The openBIM module has three workflow tabs and the existing Files tab. Steltic import retains the HR/CFS drawing importer and editable request register. IFC import reads an external model for geometry and model-data review. IFC export generates a downloadable exchange file from either source. Each tab uses the selected Hub project.

## Import and review

1. Export an uncompressed `.ifc` STEP file from the authoring application. IFC2X3, IFC4 and IFC4X3 are supported. The first version accepts files up to 100 MB and 20,000 products.
2. Inspect the file. The module records its fingerprint, schema, source units, storeys, classes, GlobalIds, materials, section information and schema/data findings. The original is preserved.
3. Review the questions. The defaults retain all objects and the declared IFC units. Structural-only scope selects structural IFC classes and walls explicitly declared `Pset_WallCommon.LoadBearing = true`; it does not infer bearing behaviour for other architectural walls. Missing length units require an explicit answer. Notes record further information; they do not invent or overwrite source properties.
4. Build the review model. IFC geometry is evaluated using its product placements, including mapped representations, and converted to metres. Native parsing/meshing runs in a separate worker with a five-minute time limit. The preview is centred to preserve display precision; source coordinates are not moved. Map-conversion metadata is retained in the IFC but is not applied to the preview. The mesh budget is 1.5 million triangles; products beyond it are listed as unrendered, never silently dropped.
5. Orbit, pan, zoom, filter by class/storey, and inspect object properties. Space volumes are hidden initially so they do not obscure building elements. Fit building focuses the initial camera on building elements; Fit all also includes proxy markers. Source objects, filtered objects and unrendered products are counted separately. Explicit polyline axes remain lines if no surface geometry exists.
6. Record the model review and notes. This records a geometry/data review, not engineering acceptance. Structural loads, supports, connection behaviour and capacity checks are outside this first IFC import release.

Missing materials, sections, storeys, geometry, duplicate GlobalIds, identical coincident geometry and IFC schema issues are reported. Some source assemblies are represented only by their child objects; a geometry-less assembly remains visible in the findings. Unknown information stays TBD. Answering scope or unit questions rebuilds a new revision; replacing the source preserves earlier IFCs and review results. Every save has a revision/fingerprint guard against stale edits.

## Architectural IFC to HR or CFS

After building the IFC review, choose **HR Steel** or **CFS Steel** under **Continue to structural design**, enter the engineering instructions, and prepare the design brief. The versioned handoff combines those instructions with explicit IFC grid polylines, storey datums, floor/roof surface boundaries (including slopes and holes), wall surfaces and explicitly supplied axes, source bearing-wall flags, door/window bounds and their host-wall references, source fingerprint and review revision. It does not infer wall centrelines from envelope bounds or choose member sizes. Source properties are evidence, not executable instructions. Missing/unrendered geometry and unsupported grid curves remain disclosed.

Download `hr_brief.txt` or `cfs_brief.txt`, then load it through the chosen module's **Design > Upload files** using the same project name. That module selects and checks the structure through its normal workflow. Once it finishes, use **IFC export** for the return model; **Steltic import** can generate drawings when needed. Preparing a handoff does not launch a paid design run. The architectural IFC alone does not establish loads, supports, structural systems, capacities or connection details. Existing HR handoffs and callers that omit the target module remain supported.

The three fictional [architectural video examples](architect-video.md) cover a regular office, a stepped school and a gabled warehouse. Their preliminary OpenSees builds are model-creation checks; the separate fresh HR office run supplies the design/drawing/return-IFC example.

## Export

Select a source in IFC export, click Generate IFC, then Download IFC. The export report records counts, geometry warnings, source/revision fingerprints and schema results. Outputs are retained under the project's `openbim/ifc/exports` directory, separate from drawing revisions.

Physical source checks are reported separately from IFC schema validation. Limited screens identify explicit built-up section count labels that disagree with their constituent geometry, opening vertices outside their declared host bounds, and connection box parts more than six feet from their assigned joint. The shared HR/CFS/openBIM validator reports these as `needs_input`, independently of a stored ready flag. Required new jobs must resolve them before completion. Legacy coordination export remains available and retains the source coordinates. The findings and their limitations travel in `Steltic_PhysicalChecks` on the IFC project; reimport displays them as source-declared findings. A result with no findings in these limited screens does not establish architectural agreement, complete framing, capacity or physical fit.

For a **direct HR/CFS job**, choose the job under **HR/CFS physical source** and click **Load job for IFC export**. This validates and snapshots its `bim_package.json`, without running the drawing engine. Generate IFC from that physical revision. Reload after updating the design job; existing snapshots and IFCs remain immutable. Concurrent source replacement and stale export requests are rejected. The output records the source module, job, physical revision and package fingerprint. It uses supplied physical geometry and the same disclosed reference-axis fallback as drawing exports. It does not adopt fictional drawing supplements or assert a design completion check merely because the package can be exported.

The local API uses `POST /api/project/{project}/ifc/structural/import` with `module`, `job` and the current physical `revision` when replacing a source. `POST /api/project/{project}/ifc/export` then accepts `source: "structural"`, `revision` and `source_sha256`. Jobs are restricted to configured HR/CFS roots; callers cannot supply arbitrary source paths. Physical snapshots are stored under `openbim/ifc/structural` and have their own current pointer. Existing drawing and imported-IFC export APIs retain their behavior.

For a **Steltic drawing revision**, the exporter writes IFC4 in metres with a project/site/building/storey hierarchy, stable product GlobalIds, classifications, material assignments, member marks, source sections, design-record references and outstanding requests. It reopens and validates the resulting IFC and checks product counts. This is a coordination IFC, not a claim of certified MVD conformance or editable native Revit families.

Source-declared HR and CFS physical models use the dimensioned coordination renderer. Missing optional opening labels are displayed as “opening”; source geometry and any explicit level are retained. Proposed openings stay marked TBD until quantitatively resolved. Exported objects without a declared numeric level remain contained in the building, rather than being assigned an invented Level 1. The export report counts these unassigned objects.

Where HR has source level elevations but no per-object labels, its existing coordination grouping is disclosed as derived rather than source-declared. Generic braced-bay or supplier-envelope panels are `IfcBuildingElementProxy` objects, with their source kind retained, instead of being misclassified as floor slabs. The top framing plan is called a roof only where a source roof panel establishes that role.

Producer declarations using an integral numeric `storey` instead of `level` retain that assignment, including zero. The coordination view records the original `SourceStorey`, `LevelSourceField` and assignment basis without changing the source package. Named, fractional, boolean or otherwise ambiguous values do not establish a numeric level. An explicit canonical `level` takes precedence. Connection parts inherit an available connection/joint assignment; objects without one remain unassigned.

- Located members use the existing design meshes. Rolled fillets, bend radii and unmodelled fabrication cuts are not added.
- Panels use source surfaces with thickness metadata. Source opening polygons export as visible `IfcAnnotation` boundaries, with their host-source IDs, explicit or host-derived levels and source records. Their full source data and coordinate units also remain in project properties. These references do not cut panel/member geometry or assert an `IfcRelVoidsElement` relationship. Unconfirmed proposed openings remain request metadata.
- Located connection parts are exported where the physical package supplies their actual geometry. Parent connection, joint and connected-member identifiers are retained. A source-declared storey on the connection or joint is preserved, including level zero; otherwise the parts remain contained in the building and their missing storey is disclosed. Unlocated connection specifications remain metadata. The locally drawn detail assemblies in the 61 fictional review PDFs are not automatically transformed into global placements without an occurrence transform.
- Recovered ordinary-job source worklines remain reference axes. Unknown section orientation, physical set-out and connection geometry are not converted into invented solids. The export tab identifies this before generation. Some receiving applications may not display all curve-only representations; use the report and the openBIM review to inspect coverage.

For an **imported IFC**, export retains the complete original object graph, schema, GlobalIds and geometry, including objects outside the selected preview scope, and adds review information. An explicitly chosen unit override changes the length-unit declaration without rescaling source coordinates or map-conversion metadata. Schema problems already in the source are reported; this path does not claim to repair them. It is not a selective export of the preview filter.

## Revit exchange

Revit exports IFC through File > Export > IFC. IFC4 Reference View is a common coordination option; IFC2x3 is also supported by the importer. A Revit file itself (`.rvt`) is not an IFC and cannot be uploaded to this tab. Linked-model inclusion, category mapping, visibility and export settings determine the content actually transferred. [Autodesk export settings](https://autodesk.ifc-manual.com/revit/ifc-export-settings-dialog).

Revit can open an IFC into a new model or link it as a reference. A linked IFC can be reloaded after changes; opening does not preserve that live link. IFC exchange does not guarantee the original parametric Revit families, constraints, analytical connectivity, supports or loads. Imported geometry must still be reviewed. [Autodesk import/link guidance](https://help.autodesk.com/cloudhelp/2023/ENU/Revit-Model/files/GUID-C61C2E42-0561-48C9-8459-3EAC10EC8E16.htm).

Validation uses IfcOpenShell 0.9.0.post1 and independently authored fixtures covering schema variants, mapped/rotated geometry, units, preserved object graphs, missing information and revision guards. Additional buildingSMART building samples are checked locally without committing external or private building files. Revit itself is not part of this automated test environment; compatibility is based on standard IFC representations and Autodesk's documented import/link support, not a claim of a completed native Revit acceptance test.

Legacy reviewed-model IFC exports accept both polygon opening boundaries in inches and recorded XY/XZ/YZ lower-left coordinates with dimensions in feet. Conversion preserves the recorded set-out, rejects invalid dimensions, and does not infer a host or cut panels. Export also retains explicit source grids and HR elevation datums, including an unoccupied ground datum. Grids recovered from analysis-column worklines are labeled as derived. Analysis occurrence IDs remain attached to their returned elements. These exchange checks do not promote an incomplete legacy model to physical readiness.
